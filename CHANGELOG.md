# Changelog

## 0.6.2

- **Tandem: today against yesterday, from a daily history in records.** The `tandem_glucose` tool (1.4.0) now ends its report with one summary row per calendar day, for up to the last 14 days it downloaded: glucose in mg/dL whatever the display unit, time in range, time below and above range, variability, GMI, the lowest and highest readings, lows and highs, insulin (total, bolus, basal), boluses and carbs, and the average and time in range overnight, in the morning, afternoon and evening. Today's row is marked as partial, with the time it runs to. The model saves the rows with `records_save` into a `tandem_daily` set keyed by date (marked as health data), so the same day saved again is updated and the history grows across conversations and scheduled runs, then compares today with yesterday through `records_lookup` (by time of day, since today is partial), and with earlier days for a trend, and leads its answer with how today is going against yesterday.
- **Tandem charts: the last 24 hours in red, the average in blue.** Both of the tool's charts (glucose over the last hours against the usual day, and time in range by time of day) draw the recent window in red and the baseline average in blue, where they used to take the palette's first two colors.
- **A chart series can name its color.** A series in `generate_chart`'s input, or in a `[chart]` line a tool prints, may carry `"color"`: one of blue, orange, green, yellow, pink, purple or red. The picture `generate_chart` saves, the web chat and the iPhone and Android apps map it onto their own palettes (Android, whose palette has no pure red, takes its rose); any other value is dropped, and a series without one takes the next palette color as before.

## 0.6.1

- **The Memory count in Settings counts every memory.** The web chat's and desktop app's Settings menu, and the iPhone and Android apps' *What Cedar Remembers* row, showed only the memories of the kind the Memory page last had open (*About you* by default), so conversations and ways of working were left out of the number. They now count every active memory, of every kind, and the count follows when a memory is removed, archived or restored.

## 0.6.0

- **The desktop app checks for updates at start-up, and says when you're up to date.** The first check now runs a few seconds after Cedar starts instead of a minute later. A check you ask for (the menu bar's or tray's *Check for Updates…*, or *Check now* on the setup page) that finds nothing newer now says so: the chat shows "You're on the latest version, Cedar X" for a few seconds, and the setup page's Updates section says the version you have is the latest. In English, German, French and Spanish.
- **Memory, revised.** Memory was a flat list of up to 200 facts, shown whole in every prompt and written only from the last message you sent; it was not useful. It is now typed and versioned, and used the way the research on agent memory says works (the design and the research behind it are in [docs/design/memory.md](docs/design/memory.md)). What is kept: facts, preferences and standing instructions you stated, each with the words of yours it was taken from, when it became true, and, for a fact with one current value (home city, employer), a key; temporary facts with an end date; an episode per conversation (what it was about and how it ended), written by the run itself; procedures (how a task with tools went well, abstracted); and a profile, a short summary of you that a background pass writes and that you can write yourself. What a run sees: the profile and every pinned row (instructions are pinned by default) in every request, plus what the request calls for: facts whose words overlap it, and earlier conversations and procedures only on a recall cue ("like last time", a date), within a token budget; a store of up to 25 facts is shown whole. Ids are short (`[m12]`) and what was shown goes out as a new `memory.recalled` event and in the trace as `memory`. A `recall` tool searches memory, with history, in every run. Writing: the call at the end of a run now reads the conversation (never tool results or files) and notes the facts you stated, each with your words as its quote, an episode, and a procedure when the work went well; a fact is saved only if the quote is in your own words (so nothing from a tool, a page or an email can become a fact about you), text that looks like a secret or an identifier is refused, the same thing said again is one row, a text that differs in one word is another, and a contradiction supersedes the old row and keeps it as history instead of overwriting or deleting it. `remember` takes `kind`, `supersedes`, `valid_until`, `subject` and `relation`; `forget` archives instead of deleting. Consolidation: after five finished runs (`MEMORY_CONSOLIDATE_AFTER`) or an hour of idleness, a background pass archives expired temporary facts, rolls raw episodes older than a month up into one summary per month, and makes one model call that merges duplicates, closes contradictions and writes the profile, conservatively (only rows of one kind that are plainly alike; never a pinned row; never a profile you wrote; every change an audit row; nothing deleted). Rank and budgets replace the hard cap: rows are ranked by kind, repetition, recall and disuse (down to a floor), and past `MEMORY_MAX_ITEMS` (now 500) the lowest-ranked is archived, not refused. New: `POST /v1/runs/{id}/feedback` (a thumbs up or down counts for or against the procedures the run was shown; the chat passes its thumbs on), `GET /v1/memory?kind=&archived=&q=`, `GET` and `PATCH /v1/memory/{id}` (edit, pin, archive, restore), `GET /v1/memory/{id}/history`, `GET` and `PUT /v1/memory/profile`, `GET /v1/memory/export` and `POST /v1/memory/import`; `GET /v1/defaults` reports the new limits. `MEMORY_EXPERIENCE`, `MEMORY_CONSOLIDATE`, `MEMORY_CONSOLIDATE_AFTER` and `MEMORY_RECALL_TOKENS` are new settings. Upgrading: the migration keeps every memory as a fact without a quote; clients from before this release keep working with the list (`id`, `text`, `run_id`, `created_at`, `updated_at` are unchanged).
- **Settings → Memory, reworked.** The web chat and the desktop app show the profile at the top, editable; the memories by kind (*About you*, *Conversations*, *Ways of working*) and the *Archive*, each with the words it was taken from, how often it was used, Pin, Archive or Restore, and Remove; and Export. In English, German, French and Spanish.
- **Memory on the iPhone and Android apps.** Settings → Memory gets the same page: the profile at the top, editable (edit it and it stays as you wrote it); a picker for *About you*, *Conversations*, *Ways of working* and the *Archive*; each memory with its kind, the words it was taken from, when it was saved, how often it was used and the conversation it came from. On iPhone, swipe a memory to pin or unpin it, archive or restore it, or delete it; on Android, long-press. *Delete All* forgets everything, the profile and the archive included. A `recall` step shows its query under the reply. In English, German, French and Spanish.
- **Records fill themselves.** Records were written only when the model chose to call `records_save`. Three paths now save without a tool call. A CSV or JSON file attached to a message (`text/csv` and `application/json` join the attachment types, in the API and the web chat's paperclip) is imported into a record set named after the file when the run starts: the first identifying column (`id`, `date`, ...) is the key, numbers become numbers, a repeat of the file updates its rows, and the agent is told where the rows went in the files note; a `records.updated` event says what was imported, `"import_attachments": false` on the run or `RECORDS_IMPORT_ATTACHMENTS=off` leaves the file in the workspace only, and `GET /v1/defaults` reports the default under `records`. The call at the end of an interactive run that notes the facts you stated also proposes the data you handed over, in your messages or your files, as rows for a set, new or existing; a row is saved only when every value of it is in your own words or files, so nothing from a tool result or a web page gets in, and `memory.updated` lists what was saved under `records` and what was refused under `skipped`. And when a conversation is turned into a scheduled agent, the compacted prompt tells the agent to save a result worth comparing over time into a fixed set keyed by date, and to compare with the earlier rows before answering, so a weekly check-in builds a series on its own.
- **cedar-bench: a memory category.** A task can hold earlier conversations (`sessions`) before its run, the runner clears the key's memory around every trial, and two new checks read what cedar remembers afterwards (`memory_item`) and what the final run was shown (`memory_recalled`). Six seed tasks: a fact stated in passing and needed later, a fact that changed, a standing instruction that must fire in an unrelated conversation, a task to repeat "like last time", a temporary fact, and a creative request where nothing remembered may leak in.

## 0.5.0

- **Records: data the agent keeps for you across conversations.** Memory holds a few facts; it could not hold a running log. A run can now save rows of data into named sets per API key (`records_save`: a set name, a description, the fields that identify a row as its key, and the rows as JSON objects), so the same week handed over twice is updated rather than doubled, and read them back with one read-only SQL query (`records_lookup`: each set the query names becomes a table of that name in a private in-memory database, with `_id` and `_saved_at` beside the fields, so a week-by-week comparison is a `GROUP BY` or a window function, and sets join on a shared date). `records_list` and `records_describe` show the sets and a set's columns with sample rows; `records_drop` deletes a set, in interactive runs only. Every run's note lists the sets it keeps (name, size, columns, description, last saved), never their contents, with the rules for using them; a set marked `health_data` brings the health rules in. Unattended runs may save and read, so a weekly scheduled agent can import on its own. `GET /v1/records` lists the sets, `GET /v1/records/{name}` the rows, `POST /v1/records/{name}` uploads rows by hand (an export can go straight in), and `DELETE` removes a set or all of them; the limits (`RECORDS_MAX_SETS`, 50; `RECORDS_MAX_ITEMS`, 10,000 per set) are in `GET /v1/defaults` under `records`. `RECORDS=off` removes the tools and the note; the `records` tool group switches them per run. Records outlive workspaces, conversations and runs, which is what makes a long-running weekly thread unnecessary: the next week can start fresh and still see every earlier one.
- **Settings → Records in the chat.** The web chat's Settings get a Records page beside Memory: the sets the agent keeps, most recently saved first, each with its description, row count, key, columns, last save and a *Health data* badge; *Show rows* opens a set's rows in a table, newest first, with the date each was saved and a link to the conversation that saved it; *Delete* removes a set and *Delete all* every set, after a confirmation. The page says when records aren't ticked under Tools, or when the cedar server predates them. `GET /api/records`, `GET` and `DELETE /api/records/{name}`, `DELETE /api/records` on the chat server.
- **Records on the iPhone and Android apps.** Settings gets a *Records* section beside Memory, shown when the chat server has them: the sets Cedar keeps, most recently saved first, each with its description, row count, key, columns, last save and a health-data mark; a tap opens a set's rows, newest first, each with its fields, when it was saved and a tap to open the conversation it came from. On iPhone, swipe a set to delete it; on Android, long-press. *Delete All* removes every set after asking. Deletions apply at once, like Memory. In English, German, French and Spanish.
- **Memory picks up what you say about yourself.** Facts were only saved when the model chose to call `remember`, which it rarely did unless asked outright. Now every interactive run ends with one short tool-free model call that reads the message you sent, next to what is already remembered, and lists the durable facts in it (your name, where you live, work, family, diet, the tools you use, how you like answers, standing instructions, ongoing projects) as JSON; each is saved as `remember` would, deduplicated and with `replaces` honoured, and the list is never read from the model's answer, tool results or attached files, only from your own words. What was saved goes out as a new `memory.updated` event (`saved: [{status, memory}]`) after the answer, shows in the chat as *remember* steps under the reply, is in the run's trace as a call with `purpose: "memory"`, and counts in a `usage` event with that purpose. `MEMORY_EXTRACT=off` turns the pass off. The rules the model is given for `remember` now tell it to save such facts in the same reply, without being asked, rather than only on request. Contributed conversations leave the memory call out, as they do the memory list.

## 0.4.0

- **Gmail and Calendar without environment variables.** The Google OAuth client cedar connects an account through can now be saved from the chat's Settings → Server, under a new *OAuth client* row next to *Google account*, like the Brave, Best Buy and SerpApi keys: cedar checks the ID and secret against Google's token endpoint, keeps the secret encrypted (`CEDAR_SECRET_KEY`), and offers the tools as soon as the account is connected, without a restart. The row walks through the Google Cloud console in three steps and takes the JSON file the console downloads, pasted into either field. On the desktop app that is the whole setup: `GMAIL`, `CALENDAR`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` no longer go into `config.json`. `PUT` / `DELETE /v1/admin/integrations/google/client` on cedar, `PUT` / `DELETE /api/integrations/google/client` on the chat; `GET /v1/admin/integrations` reports the client under `google.client`. A client in the environment still wins and shows as managed there.
- `GMAIL` and `CALENDAR` are now on by default and wait for a client and an account; `off` removes the tools as before. A server that set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` without turning them on now offers them. The tool catalog says *Needs a Google OAuth client* until one is set up, and "Connect Google" answers `409` with the same.
- **"Connect Google" from the chat's own computer uses the loopback address.** A browser that opened the chat at `http://127.0.0.1:…` or `http://localhost:…` (the desktop app's window) is sent back there after Google's consent page instead of to `CHAT_PUBLIC_URL`, which an OAuth client of the *Desktop app* kind accepts without registering a redirect URI, also while the desktop app shares the chat over Tailscale. Any other browser keeps `CHAT_PUBLIC_URL`, and the Server page shows the redirect URI it will use.
- Replacing the Google client with a different one, or removing it, disconnects the account, whose token belongs to the client that got it.
- **Google Drive, Docs and Sheets.** With the same Google account, the agent now reads the user's files: `drive_search_files` finds them by content, name, kind, folder and date; `drive_read_document` reads a Google Doc as Markdown, Slides as text and text, CSV and JSON files as they are, in parts for long ones; `drive_download_file` saves any file into the workspace (a Doc as docx or PDF, a Sheet as xlsx or CSV, Slides as pptx) for the sandbox tools; `sheets_get_spreadsheet` lists a spreadsheet's tabs and `sheets_read_range` reads a tab in windows of rows or an A1 range. Two new tool groups, `drive` and `sheets`, on by default with the others (`DRIVE=off`, `SHEETS=off`, `DRIVE_TOOLS`, `SHEETS_TOOLS`); nothing writes to Drive. "Connect Google" now asks for `drive.readonly` too, and the Cloud project needs the Drive and Sheets APIs. See [Google Drive, Docs and Sheets](README.md#google-drive-docs-and-sheets).
- An account connected before this release lacks the new scope: the Server page says which scopes are missing and *Reconnect* grants them (`GET /v1/admin/integrations` reports `google.missing_scopes`), and a tool call Google refuses for scopes says so.
- **Contribute a conversation to a training corpus, opt-in.** The chat can give single conversations to a corpus for training open-weight agent models, and only when three things are true: the chat has a corpus (the project's own unless whoever runs it named another or set `CHAT_CONTRIBUTIONS_URL=off`), you have read and turned it on under Settings → *Contribute* (choosing a license, CC0 or CC BY 4.0, and whether to use a random pseudonym), and you chose *Contribute this conversation…* in the More menu and clicked *Send* in the review dialog. The dialog shows exactly what would leave your server, built from the runs' traces: the memory list is cut from the system prompt, attached files and their names dropped, fetched page bodies and the model's reasoning left out unless you include them, identifiers and exact times removed, and emails, phone and account numbers, IP addresses, keys and home-directory names replaced by made-up stand-ins of the same shape (an address at example.com, a 555 number, an invented name), the same for the same value throughout the conversation and never derived from it, so the sample reads like a real one and a model trained on it learns the shape of data rather than bracket tokens; the bundle lists which values are stand-ins. You can redact any phrase and say what replaces it, rate each response with a thumb, and say whether the agent did what you asked; *Exactly what is sent* is the document that goes, byte for byte, and *Download JSON* saves it. Conversations of scheduled agents, ones that used Gmail or Calendar, and ones in which a secret remains cannot be sent. Receipts in Settings let you withdraw a contribution. With the corpus off, expert mode offers the export as a download. See [PRIVACY.md](PRIVACY.md), [chat/README.md](chat/README.md#contributing-a-conversation) and [docs/design/contributions.md](docs/design/contributions.md).
- A new crate, `cedar-contrib-schema`, holds the bundle format (schema version 1, with a canary string every bundle carries), the consistency checks both sides run (tool calls and results pair up, call counts grow, token counts fit the bytes sent, events are in a legal order, declared stand-ins occur in the text) and the pattern scan for secrets and personal data. `contrib/` is `cedar-contrib`, the ingest a corpus runs: `POST /v1/contributions` checks a bundle the same way, applies per-pseudonym and look-alike quotas, catches duplicates by content hash and stores the bundle in a quarantine bucket with a receipt; `DELETE` withdraws it with the receipt's token, which is derived, never stored. It keeps no request logs. A Dockerfile and Terraform for Cloud Run are in `contrib/` (see [contrib/README.md](contrib/README.md)).
- **The corpus side: screening, review and releases.** `cedar-contrib screen` gives every quarantined bundle a verdict with flags, scores and notes: near-duplicates by MinHash (another contributor's is held, one's own resubmission rejected), zero-width, bidi and mixed-script triggers, long encoded runs, injected instructions in tool results (with a judge model saying whether the agent complied; complied is rejected, resisted is accepted and tagged), destructive and exfiltrating commands, self-reported outcomes that contradict the run's own ending, floods of look-alikes from one pseudonym, personal data the client missed, the wrong language, threads too thin to train on. A judge's reading of the outcome accrues label trust per pseudonym. A red-team fixture set is the regression suite. With `CONTRIB_REVIEW_TOKEN`, `/review` lists what is held with the screener's notes and takes Accept or Reject; every decision is an audit line. `cedar-contrib release` builds a monthly release: accepted bundles aged 14 days, re-screened if the checks moved on, clusters that are all one pseudonym or all unlinked held as a set, no pseudonym over 1% and the unlinked under 20%, label weights with the judge's outcome standing in for untrusted labels, one file per license and model, a manifest with every entry and the exclusion list of withdrawn hashes, and an HMAC signature. `contrib/scripts/publish.sh` mirrors a release to Hugging Face (history squashed) and a GitHub release; the Terraform runs both jobs on Cloud Scheduler. In the chat, Settings → Contribute shows what became of each contribution (*Refresh status*).
- **The steady state and the apps.** `cedar-contrib ablation` writes a release's candidate batch as training sets, with and without each cluster, runs a hook per set (the trainer and cedar-bench's safety suite live there) and holds the batch or a cluster whose presence lowers safety; without a hook it writes the sets only. `cedar-contrib stats` prints and keeps the numbers the corpus is run by (receipts by status, submissions per day, held and rejected rates, flags, contributors, waiting times, reviewer decisions). `screen --force` is the quarterly pass over everything accepted or held, scheduled in the Terraform, which also gains the optional edge (a load balancer with Cloud Armor) behind `edge = true`. The iPhone and Android apps get *Contribute this conversation* in a chat's top bar (the review with turns, stand-ins, outcome, thumbs and Send) and Settings → Contribute (the choices, the switch, the receipts with their status and Withdraw).
- `contrib/training/`, a uv project (`uv run --project contrib/training cedar-contrib-train ...`): a worked example of training a small Qwen model on a release, rejection-sampling fine-tuning on the trajectories (rewarded from outcomes, thumbs, run endings and label weights) and then GRPO on the prompts with format, judge and safety rewards; `--dry-run` shows the converted data without a GPU.
- cedar's `GET /v1/runs/{id}/trace` now says where the user's memories sit in the system prompt (`memory_note: {start, end}`), so a client that passes the prompt on can cut exactly that.
- Upgrading: cedar-chat's database migration adds a `rating` column to turns and a `contributions` table; it runs on start.
- **`plan_trip` finds the morning train.** Asked late at night for a trip between cities, the tool showed only the night coaches, 7½ hours via Leipzig for Munich–Berlin, and never the direct ICE: it took the planner's default of five itineraries, which the same coach with different local legs at either end filled before the search window reached the morning. It now asks for twelve, keeps one itinerary per trunk (the long legs), and shows the three fastest. The tool also tells the model that "now" suits only a trip about to start, so with no time named it passes a sensible departure and says which. And the model's own choice among the options is now cut off at the tool timeout (`TOOL_TIMEOUT_SECS`, 60 s), after which the fixed rules decide; a slow local model used to stall the tool for the model client's full timeout and retries, 13 minutes in one run.

## 0.3.0

- **Cedar remembers you.** The agent keeps a short list of facts about you across conversations (your name, preferences, standing instructions, ongoing projects), so a new conversation no longer starts from nothing. It saves one with the new `remember` tool when you tell it something lasting or ask it to remember, updates or drops one with `remember`'s `replaces` and `forget`, and every run is shown the whole list, framed as your facts rather than instructions. Only interactive runs may change memory; scheduled agents read it but cannot write it, and the model is told never to save what a page, email, document or tool said. The list is capped at `MEMORY_MAX_ITEMS` (200) items of 500 characters, and a full list is refused rather than trimmed silently. `GET /v1/memory` shows exactly what the model sees, and `DELETE /v1/memory/{id}` and `DELETE /v1/memory` forget one item or all; `POST /v1/memory` adds one by hand. Memory stays in cedar's database and never goes to a third party (see [PRIVACY.md](PRIVACY.md)). It is a new tool group, `memory`, on by default; `MEMORY=off` removes it.

It samples recent AI posts through the X API v2 recent search, spread over the window (24 hours by default) in slices ordered by relevancy, leaves out reposts, crypto spam, near-duplicates and more than three posts per account, and ranks stories by distinct accounts and engagement: models (GPT-6, Claude Opus 5, Qwen3, ...), companies, people, hashtags and phrases, with topics that share most of their posts grouped into one story. It compares with the window before for rising, new and cooling stories, lists the most engaged posts, the most shared links and the accounts drawing the most engagement, can add the AI entries of X's own trends (`woeid`), saves a Markdown digest to `ai_trends/` and draws charts of the top and rising topics. `topics` or a raw `query` narrows it to one area. It needs `X_BEARER_TOKEN` from an X API plan with recent search; `max_posts` bounds the posts each call reads.
- Fix: the Mac and Windows app brings its window to the front when it starts. On a Mac it opened behind the frontmost app, as a menu bar app, so you had to click *Open Cedar* in the menu bar to see it.
- Release: the DMG and MSI build faster. Every release compiled everything from scratch, since a Rust cache saved by the release pull request is out of reach of the next one; `release-cache.yml` now saves the dmg and msi jobs' caches on `main` (when dependencies change, and twice a week so they aren't evicted), and the release restores them. The desktop app builds with thin instead of fat LTO, which took several single-threaded minutes in each build.
- **OpenShell sandboxes, opt-in, with a network policy per program and host (#122).** On Linux and macOS an admin can run conversations' sandboxes, personal tool calls and tool installs in [NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell) sandboxes instead of plain Docker containers: Settings → *Advanced settings* (a new page in the web chat and the Mac app) → *Run sandboxes with OpenShell*, or `PUT /v1/admin/settings` with `{"sandbox_runtime": "openshell"}`. cedar checks that OpenShell's gateway answers before it switches, and says why when it can't. Under the switch, *How to install OpenShell* gives the commands for the OS cedar runs on (macOS or Linux), with a Copy button for each. Docker stays the default, and the only runtime on Windows, where OpenShell doesn't run: the switch is greyed out there, with a note why. A switch applies from the next message: a conversation's kept container is replaced by a sandbox on the same workspace volume, so its files come along, both ways.
- In an OpenShell sandbox no process has a network of its own: each connection goes through OpenShell's supervisor, which checks the program and host against the sandbox's policy. `SANDBOX_POLICY` picks it: `offline` reaches nothing, `packages` lets Python reach PyPI and Node.js reach npm, and a path names a policy file of your own (presets in `sandbox/policies/`). Unset, it follows `SANDBOX_NETWORK` (`none` is `offline`, a network `packages`). On Docker, any policy but `offline` still gives the container all of `SANDBOX_NETWORK`, as before.
- **Blocked connections are reported and can be allowed (OpenShell).** When the policy refuses a connection, the tool result says which program tried to reach which host, and the run gets a `sandbox.denied` event. In a run with someone to ask, cedar asks (*Let curl connect to example.com:443*); *Allow* adds that program and host to the sandbox's policy for the run, *Always* also for later runs of the same key, and the model is told to try again. On OpenShell this replaces the yes-or-no question before running code with a network; on Docker that question stays.
- **Personal and registry tools only reach the hosts they declare (OpenShell).** Each call's sandbox lets the tool's Python reach those hosts on ports 80 and 443 and nothing else, and tool installs reach only PyPI. On Docker a tool that declares hosts still gets `TOOLS_NETWORK`.
- `run.started` names the sandbox's `runtime`, `policy` and `hosts` too, and `GET /readyz` checks the OpenShell gateway when sandboxes run on it. New settings: `SANDBOX_POLICY`, `OPENSHELL_BIN` and `OPENSHELL_WORKSPACE`.
- Setting OpenShell up: install it and run its gateway with `allow_driver_config = true` (and `supervisor_network_mode = "bridge"` on Docker Desktop); see *OpenShell sandboxes (opt-in)* in the README, DEPLOYMENT.md and desktop/README.md. The sandbox image's working directory is now `/sandbox` (cedar runs commands in `/workspace` either way); rebuild it with `docker build -t cedar-sandbox sandbox/`. The web browser tool always runs in its own Docker container, since a browser needs to reach any site.
