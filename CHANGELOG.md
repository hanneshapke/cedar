# Changelog

## Unreleased

- **The desktop app starts Tailscale when it isn't running.** With *Share with the phone apps over Tailscale* on, the app used to report that Tailscale didn't answer and start without sharing. At its start it now opens Tailscale's app when the CLI gets no answer (macOS and Windows), runs `tailscale up` when Tailscale is turned off, and waits up to 45 seconds for one that is still connecting, as when both start at login. Logging in is still yours.

## 0.12.0

- **Computer use.** With `COMPUTER=on`, a model that reads images gets a `computer` tool: a desktop on a virtual screen (Xfce with Firefox and LibreOffice, the new `cedar-computer` image) that it works through screenshots, the mouse and the keyboard, for what only exists behind windows. Each run gets its own, started on first use and removed with the run, with the conversation's workspace mounted, so files move between the desktop and the other tools. Off by default; see "The computer" in the README, and its safety notes before giving the desktop a network.
- **Computer use on your own computer.** With `COMPUTER_RUNTIME=native`, or *Let Cedar use this computer* in the desktop app, the `computer` tool works the computer Cedar runs on instead of a container: your real screen, mouse and keyboard, for what only exists in your own applications. Every call waits for your OK (the new `computer` approval rule; *Always* lasts for that reply only), unattended runs are not offered it, and one run at a time has the screen. On a Mac, Cedar needs the Screen Recording and Accessibility permissions. An admin can switch between the container and the server's own computer under Settings → Advanced (`computer_runtime` on `PUT /v1/admin/settings`), from the next message and without a restart. See "The user's own computer" in the README.
- **Saved actions work with the computer tool.** An action is no longer only a website: it says what it is carried out with (a website, an application on any desktop, or your own computer) and which application it happens in, and the Actions page has fields for both. The model that writes the steps from a recording is told whether Cedar has a computer tool and whose desktop it works, instead of being told there is no desktop. A run is told which of its actions it can't carry out with what it has. Up to 6 pictures of a recording can be kept with an action, picked by the model and shown to you first; a model that reads images gets them with the steps. And on your own computer, a saved action is asked about once, with its steps on the card, instead of before every click. Your own computer comes first: an action in an application is saved for it unless you say any desktop would do, and the desktop in a container is what runs nobody attends get.
- **A tool result can carry an image.** A `tool_result`'s `content` is then a list of a `text` and an `image` block, and the `tool.result` event says `image: true`. The model is sent the image right after the tool results, only the newest three to five such images stay in a request, and an image now counts as about 2,000 tokens when a conversation is fitted to the context window, whatever its file size (an attached photo used to count by its bytes).
- **Show Cedar how: actions from a screen recording.** When Cedar can't do something, you can now show it instead of only reporting it. The chat has a new **Actions** page (in the sidebar, and behind **Show Cedar how** on the card of something it couldn't do): pick *One window* or *Entire screen*, do the task yourself, and stop. The recording is made small in your browser first (captured at a few frames a second and at most 1600 pixels a side, then cut down to the frames in which the screen changed, at most one a second and 1200 pixels a side), and a model that can watch it writes the steps: the video itself goes to a model marked *Takes video* under Settings → Models (`"video": true`, sent as a `video_url` part), the key frames to any other model that takes images. You read the steps, correct them and save them; from then on runs are told which actions you saved and read one's steps with the new `saved_actions` tool. A video file from your computer's or phone's own screen recorder works too, for browsers that can't record. Over the API it is `/v1/actions` and `POST /v1/actions/draft`; `ACTIONS=off` turns it off.
- **The Mac app records the screen for Actions.** The app's window can't share the screen the way a browser does, so on a Mac (macOS 15 and later) the app now records for the page: *Entire screen* (the display you pick, when several are connected), with your clicks shown, stopped from a red light in the menu bar (Cedar's window hides while it records, and comes back when you stop). macOS asks once whether Cedar may record the screen; quit and reopen Cedar after allowing it. The recording is handed to the page, reduced there to its key frames like any other, and deleted.
- **Show Cedar how, on every exchange.** Each message you send has a small **Show Cedar how** button beside it, which opens the recorder with that message as what you are about to show. It is there whether or not the model reported that it couldn't do something.
- **The card for what Cedar couldn't do sits below the answer.** It used to appear where the model made the call, so the answer written after it pushed it out of sight; it now moves under the reply when the reply is done. Cedar is also told to report an act it has no tool for (buying, booking, signing in) within its first few calls instead of searching around it.
- **Requests to act go to the biggest model.** With automatic model selection, a request to buy, book, pay for, order or cancel something starts on the biggest registered model instead of the smallest, and so does the moment of giving up: when the smallest model wants to report that it can't do something, the turn is asked again of the biggest. Small models tended to say "I can't" in plain text, without the report that shows the card.
- **Cedar is told more firmly to say what it couldn't do with its tool.** A reply that only says "I can't" in its text shows no card, and so no *Send feedback* and no *Show Cedar how*; the prompt now asks for the `report_limitation` call every time, before the answer.
- **A password can be stored with an action.** A password typed in a recording shows only as dots and is never written into the steps. Store it with the action and Cedar can sign in on its own: it is encrypted on the server (`CEDAR_SECRET_KEY`), the model never sees it, and the `browser` tool types it (`"secret": "<action>/<name>"`) only on that action's website, so a page can't talk the model into typing it elsewhere. Deleting the action deletes it.
- **A password field's contents are no longer part of what the browser tool describes.** A filled-in password field used to appear in a page's text with its value; it now reads `(filled in)`. Rebuild or pull the browser image (`cedar-browser`) to get this and the typing of saved passwords.
- **"Today" and "tomorrow" are the user's, not UTC's.** A run was told the server's UTC date as if it were the user's, so asked on a Saturday evening in Portland (already Sunday in UTC) what the symphony plays "tomorrow", it looked up Monday and said the concert starting that hour had already happened. A run can now name the user's time zone (`"timezone": "America/Los_Angeles"` on `POST /v1/runs`, kept by continuations, `DEFAULT_TIMEZONE` otherwise) and is then told their local date, time and offset, and that relative dates follow it. Without a zone the run is told the date is UTC's and that the user's may differ by a day. The memory notes written after a run, the `flights` tool's date check and personal tools (`CEDAR_TIMEZONE`) use the same date. The chat sends the browser's or phone's zone with every message (the web interfaces, iOS and Android) and keeps the last one for agents and Slack; an agent with its own zone other than `UTC` uses that. A chat server from this release sends `timezone` to cedar, so update cedar first. See [Time zones](README.md#time-zones).
- **Private chats.** For something you want neither remembered nor kept: the composer of every web interface has a *Private* button that makes the chat about to start a private one, and so does a new chat in the iOS and Android apps. A private chat is in no conversation list, Starred list, search or inbox; Cedar is shown nothing from memory in it and saves nothing to memory or records; no trace of its model calls is kept; nothing about it is sent as a notification (no push, mail, Pushover, desktop or in-page notice); and it can't be starred, contributed or turned into an agent. It is deleted, with its runs and workspace on cedar, when you leave it (*End chat*, opening another conversation, *New*), a response still being written included, and one that was never left (a closed tab) is deleted once it has been idle for `CHAT_PRIVATE_TTL_SECS` (a day). Reloading the page keeps it. In the API it is `{"private": true}` on `POST /api/conversations`, and on cedar `"private": true` on `POST /v1/runs`: such a run gets no `memory` or `records` tools and imports no attachments, `GET /v1/runs/{id}/trace` answers `404` for it, it takes no `callback_url`, and every run that continues it is private too. The iOS and Android apps have it too: on a server that has private chats (`private_chats` in `GET /api/config`), a new chat has a *Private Chat* button in its top bar, and the chat is deleted when you go back to the list or open another one.
- **Presentations in Google Slides.** Ask for a deck and the agent makes one in your Drive: it writes the outline, slide by slide, and cedar does the design. `slides_create_presentation` takes a title, a theme (`minimal`, `midnight`, `editorial`, `forest`, `bold`), an optional brand colour and footer, and slides in ten layouts (`title`, `section`, `bullets`, `columns`, `stats`, `quote`, `table`, `image`, `steps`, `closing`) with speaker notes; cedar places everything on one grid, picks text sizes that fit, and warns about slides that are too full. `slides_append_slides` adds slides to a deck cedar made and `slides_get_presentation` reads one's outline. A new tool group, `slides`, on by default with the other Google ones (`SLIDES=off`, `SLIDES_TOOLS`, `SLIDES_API_URL`). "Connect Google" now asks for `drive.file` too (cedar can create files and change only the ones it created), so connected accounts need a *Reconnect*, and the Cloud project needs the Slides API. See [Google Slides](README.md#google-slides).

## 0.11.0

- **The Slack app can be set up in Settings.** An admin pastes the app's two tokens into Settings → Slack; they are checked with Slack, saved, and the app connects at once, without a restart, and can be replaced or removed the same way. This is how the desktop app gets Slack. Tokens set in the environment (`CHAT_SLACK_APP_TOKEN`, `CHAT_SLACK_BOT_TOKEN`) still win, and Settings says so.
- **Memory as a graph.** Settings → Memory has a new *Graph* view: every memory is a mark, and a line joins two that came from the same conversation, share a topic, were used together in a reply, or replaced one another. Bigger marks weigh more when cedar decides what to recall; pinned ones wear a ring and archived ones are hollow. Choosing a mark shows the memory with its usual actions (pin, archive, remove) and what it is linked to and why; the legend hides and shows each kind of mark and line, and *Include the archive* adds what was replaced. Over the API it is `GET /v1/memory/graph` (`{nodes, edges, total, left_out}`), built per request from what memory already stores, so nothing new is kept. On the web and in the desktop app; the phone apps keep the lists.
- **An outbox for what agents would send.** An agent's run has nobody to ask, so until now it either had no tools that write or acted unseen. A run can now hold its writes (`"hold_writes": true` on `POST /v1/runs`): a call that would send or change something in a connected account (the Gmail, Calendar, Drive, Sheets and Slack tools that write) is not made but kept, exactly as the model wrote it, and the model is told to go on and say what is waiting. `GET /v1/held` lists what waits; `POST /v1/held/{id}` approves it, which makes that call, or the one you edited it into, with no model involved, or discards it. In the chat, every agent made from now on holds what it sends (a setting in its form; existing agents keep acting at once until you turn it on), the Agents page shows *Waiting for your approval* with **Approve**, **Edit** and **Discard**, and a run that left something there is announced as *waiting for your approval*. The iOS and Android apps show the same list above their agents, the card in a run's conversation, and the switch in the agent form; they approve or discard, and editing a held call before it goes out is on the web.
- **An approval nobody answered no longer drops a message.** When an interactive run's approval times out, a mail, a calendar change or a Slack post it wanted to make is kept in the outbox instead of being skipped.
- **You are told when a response needs your OK.** A response that stops for an approval or for its plan used to wait on the page alone, for five minutes. The chat now follows the run of every message sent from the page: other tabs say so at once, and a wait still unanswered after `CHAT_ATTENTION_DELAY_SECS` (20) goes out by your notification method with what the call would do.
- **"Always allow" is earned.** An approval offers *Always for …* only after the same thing (a host, a package, a community tool's release) was allowed `ALWAYS_ALLOW_AFTER` times (3) since it was last declined, and the card says how many more it takes. `approval.required` carries `always: {scope, allowed, after, offered}`, and its `scope` is `null` until "always" is offered, so clients from before simply don't show the button. `ALWAYS_ALLOW_AFTER=0` is the old behaviour.
- **Cedar says what it couldn't do, and you can send that as feedback.** A new `report_limitation` tool lets the model note a request it could not carry out: no tool for it, an account that isn't connected, a site that refused it, a limit it hit. The tool records nothing. The chat shows the note as a card with **Send feedback** and **Dismiss**; what you send stays on your server under Settings → Feedback, counted by category, where whoever runs it sees which tools and connections people miss (`GET /api/feedback`, with `?users=all` and the admin token for everyone's). The iOS and Android apps show the card too. `FEEDBACK=off` removes the tool. A sent report can also go to the project: **Report it to the project** opens a new GitHub issue with the report filled in, which you read and submit yourself with your own account; the server sends nothing (`CHAT_FEEDBACK_ISSUES_URL` names another repository, `off` removes the link).
- **The system prompt knows how each run hands over.** An interactive run is told which calls wait for an OK, to write them complete and final, and not to route around a declined one. A run that holds its writes is told they wait in the outbox and are sent as written. Any other unattended run is told to act only where its prompt says to. Every run is asked to end an answer that leaves something open with what is left for you, and the default prompt asks Cedar never to describe something as sent, booked or changed unless the tool's result says it was.
- Registry: new tool `ticketmaster_events`, live events from Ticketmaster's Discovery API (concerts, sports, theatre, comedy, family shows, also Live Nation, Universe and TicketWeb). It searches by keyword, city, state, country, postal code or latitude and longitude with a radius, a date range in the venue's local time, a segment or genre, sorted by date, relevance or distance, and returns each event's local date and time, status, genre, venue, distance, performers, price range when listed, public on-sale time, an image and its Ticketmaster link, with repeat listings of the same show (packages, resale) folded together. `event_id` reads one event's details: address, every price range, presales, ticket limits, age rules, doors and the seat map. It can't buy tickets. It needs `TICKETMASTER_API_KEY`, the free Consumer Key of an app on developer.ticketmaster.com.
- **cedar picks the model.** The chat no longer asks which model a message goes to. With one model registered, it is used; with several, cedar reads their sizes off their names (the parameter count: `qwen3:4b`, `Llama-3.3-70B`) and gives planning, reviewing (compacting a conversation), complex tool calls (code, files, the browser, anything that sends or changes something) and long tasks to the biggest model, and everyday requests to the smallest. A run starts on the smallest model; when it reaches for a complex tool the turn is asked again of the biggest, which keeps the run. Settings → *Advanced settings* → *Choose the model yourself* brings the pickers back, with everything as before (the iOS and Android apps hide and show their pickers with it); over the API it is `model_selection` on `PUT /v1/admin/settings`, and a run that names a `model` or a `reasoning` level always gets what it names. **Changed:** with more than one model registered, a run that names neither no longer gets the default model unless that setting is on.
- **Talk to Cedar from Slack.** With a Slack app's app-level and bot tokens (`CHAT_SLACK_APP_TOKEN`, `CHAT_SLACK_BOT_TOKEN`), cedar-chat answers direct messages to the app and mentions of it in channels, in the message's thread. Each thread is a conversation, listed on the page like the others, and replies in it continue the run. Plans and tool approvals are posted in the thread with buttons only the asker can press, `stop` cancels a response, and the answer comes back in Slack's markup. The app connects over Socket Mode, so Slack never has to reach the server. Nobody's messages reach Cedar until they link their Slack account to themselves here, with a code the app sends them, in the new Settings → Slack. See [chat/README.md](chat/README.md#slack), which has an app manifest.
- **Everyone connects their own Google account.** On a server with more than one user, the Google account under Settings → Server is now the primary user's alone. Each other user connects theirs under Settings → Tools (*Your Google account*, no admin token needed, through the OAuth client the admin saved), and their messages and agents get Gmail, Calendar, Drive and Sheets tools that act for that account only; until then they have none, so nobody's runs read someone else's mail. In cedar these are `GET`/`DELETE /v1/google`, `POST /v1/google/authorize` and `POST /v1/google/callback`, for a user named in `X-Cedar-User`; a key's own runs keep using the server's account. Changing the OAuth client disconnects every account connected through it. The Slack token is still shared.
- **Pairing a phone no longer shows other users the shared access token.** Settings → Phone handed `CHAT_ACCESS_TOKEN`, the primary user's, to whoever opened it. A user who is not the primary one now gets their own token there and in the QR code, so their phone signs in as them.
- **The groundwork for more than one person on a server.** cedar-chat now has users: `POST /api/users` (with the admin token) adds one and answers with their own access token, and everything a person makes is theirs alone, here (conversations, agents, settings, notification devices, contribution receipts) and in cedar (runs, traces, memories, records). cedar takes the user from an `X-Cedar-User` header, which only a key in the new `CEDAR_SERVICE_KEYS` may send, and gives such a key one stream of every user's finished runs (`GET /v1/events?users=all`). A server with one user changes nothing: what was there belongs to the primary user, who is still whoever has `CHAT_ACCESS_TOKEN`, and whose runs and memories stay under cedar-chat's own key. Models, integrations (the Google account, Slack) and personal tools are still shared by everyone on the server, and users are managed over the API only.
- **The phone apps are released only when they change.** Cedar, the Android app and the iOS app share `major.minor` and now count patch versions on their own: a release ships the platforms whose version it bumps (`scripts/bump-version.sh` picks the ones that changed), each under its own tag (`v…`, `android-v…`, `ios-v…`). So 0.11.2 on the desktop next to 0.11.0 on a phone is the same Cedar 0.11, and a desktop fix no longer sends an unchanged app to TestFlight.

## 0.10.1

- **The run time limit can be changed in Settings.** Settings → *Advanced settings* → *Run time limit* sets how long a reply may take, tools included, before cedar stops it (60 seconds to a day), from the next message; empty goes back to `RUN_TIMEOUT_SECS`, which is now only the default. Over the API it is `run_timeout_secs` on `PUT /v1/admin/settings`.
- **A tool that keeps failing is left out.** A tool that fails twice in a row for a temporary reason (rate limited, unavailable, timing out) is not run again in that run; further calls answer at once that it was left out. In a daily-digest run on a 32k model, twelve calls to a rate-limited arXiv took 337 of the run's 600 seconds. The community `arxiv_search` tool (1.2.0) also says plainly that a 429 or 503 is not the query's fault, names arXiv's listing pages to read instead, and gives up after 20 seconds instead of 60.
- **The model is told when time runs short.** From 60 % of the run's time limit on, or with three turns or fewer left, each turn's results end with a note on what is left and to produce the result from what the run has, since a stopped run delivers nothing.
- **A turn's independent tool calls run at the same time.** Searches, pages and other calls without side effects run together; sandbox, browser, memory, records, download and account-changing calls still run one at a time, in order.
- **Cutting a conversation down keeps the server's prompt cache.** A cut is made the same way in every later request, and a conversation is cut to 70 % of what fits, so llama.cpp and vLLM can reuse what they computed for the start of the prompt instead of reading most of it again every turn.
- **Fewer tokens per page.** `fetch_url` drops menus, sidebars and the page's own header and footer, and reads a GitHub repository's releases page from the GitHub API (tags, times and notes, without the lists of downloads).
- **The date is harder to miss.** It now heads cedar's part of the system prompt, with a request to use it and its year for anything recent.

## 0.10.0

- **Runs fit the model's context window.** A model entry now has a `context_window` (prompt and reply together), which cedar asks the server for when the entry is saved (vLLM's `max_model_len`, llama.cpp's `/props`) and `cedar-llama` sets to the 32,768 tokens it starts its models with. A run then asks each reply for what the window leaves instead of the full `max_tokens`, shares what is left among a turn's tool results, and cuts older tool results down (then the newest, then old messages) before a request would overflow; a `context.trimmed` event says what was cut. Before, a run on a 32k model could send 31,500 tokens of prompt with `max_tokens: 32768`, get a reply cut off mid-thought, and be marked completed with no answer.
- **A reply cut off before it answered is no longer an answer.** When the window cut it short, the turn is tried once more with less of the conversation; if that fails too, or the reply spent its own limit thinking, the run fails with an error that says which. The memory call is told how a run really ended: an episode's outcome is `no answer` or `cut off` where it was, and no procedure is learned from such a run. The memory call also runs at the model's lowest reasoning level with at most 4,096 tokens.
- **Small windows get a smaller prompt.** With a window of 65,536 tokens or less, a run that may use every tool is offered the ones its request seems to need (the sandbox, web, memory and records tools, plus the groups and tools it names), is asked to work through a task one source at a time, and is shown the profile and the memories its request calls for rather than the whole store. Unattended runs no longer list the whole store beside the profile either. Every run's system prompt now carries the current date and time.
- **Fewer tokens per web page.** `fetch_url` lays tables out without borders and leaves navigation links (`hide?id=…`, `login`, anchors) out of the list of links, which lists each address once and absolute. Hacker News's front page comes from its search API as a compact list. The community `arxiv_search` tool (1.1.0) returns the first sentences of each abstract unless asked for `full_abstracts`.

## 0.9.1

- **The reply limit of the app's llama.cpp model can be raised.** In the desktop app, the model's row under Settings → Models had no form, so its 8,192 tokens per reply could not be changed there, and the app registered that limit again on every launch. The row now has **Reply limit…**, a slider up to the model's context of 32,768 tokens, and the app sends its own limit only when it first registers a model (or after another model is installed).
- **Settings shows how fast a llama.cpp model writes.** `llama-server` is now started with `--metrics` (by the desktop app and `cedar-llama serve`), and a model's row under Settings → Models says whether it is writing a reply, its average tokens per second and how many tokens that makes in the 300 seconds a reply may take, how fast it reads, how much it has written since it started and the fullest its context has been. cedar reads it at `GET /v1/admin/models/{id}/stats` (`/api/integrations/models/{id}/stats` on the chat server); a server without such a page shows nothing. A llama.cpp server of your own needs `--metrics` to show up.

## 0.9.0

- **The desktop app can run a model on this computer's GPU with llama.cpp.** When the graphics card has 12 GB or more (or the Mac 32 GB or more), the setup page offers to download a pinned llama.cpp build and a model that fits, checks that `llama-server` finds the GPU, and runs it as a model server of its own beside cedar and cedar-chat, restarted like them. The download shows its progress, can be stopped and continues where it left off; every file's size and SHA-256 are checked before it is used, and *Remove* takes it all away again. All four models read images and come with their vision projector: Gemma 4 12B for 12 and 16 GB, Gemma 4 26B-A4B for 20 GB (and a 32 GB Mac), Qwen3.6 35B-A3B from 24 GB, Qwen3.5 122B-A10B from 80 GB (a 128 GB Mac). The model the app runs is a registry entry of its own (`llama`), so setting it up doesn't replace a model server named on the setup page, and a default chosen later in the chat's Settings stays.
- **`cedar-llama` for Linux.** The same choice of build and model as a command: `cedar-llama detect` says what the GPU can run, `install` downloads it and `serve` runs `llama-server`. The Linux tarballs include it, with a systemd unit.
- **Three ways to choose a model.** The setup page's model step, and *Add a model* in the chat's Settings, now offer: run a model here with llama.cpp (greyed out, with the reason, where it can't be done), use a hosted provider (recommended when this computer can't run a model), or use a model server you already run. The hosted form lists fifteen providers with the address each one documents and a link to that documentation, takes the key, suggests a model once the provider's models are listed, and narrows the long list as you type. The own-server form has presets, now including llama.cpp and SGLang, that fill in the address, say what the server needs and list its models at once. The choice is saved as `model_source` in `config.json`. Providers and presets are served by cedar-chat at `/model-servers.json`.
- **Cedar works out whether a model reads images.** Adding a model no longer asks: a list of known models says, and cedar tries a model it doesn't know with one small image when it is saved (`detect_images` on `PUT /v1/admin/models/{id}`). Settings shows the outcome and keeps a way to say it outright under *Advanced*. The desktop app now registers hosted and own servers the same way, where it used to register them as text only.
- **A simpler model form in Settings.** The reasoning levels follow the chosen model and show as one line, with the usual sets and the default level under *Advanced* (and *Other…* for a list typed by hand); the reply limit is a slider from 1,024 to 131,072 tokens. Model lists that come back as a bare array, as some providers send them, are now read by cedar and the app.
- **One install guide.** The website's install and model pages are merged into one guide that asks about the computer, shows the three ways to get a model with what each means for it and which one the app would recommend, and gives the steps; it also covers connecting to a Cedar that already runs on another computer. Old links to either page keep working. The model guide's commands use llama.cpp in place of Ollama (except on the Jetson), and the landing page shows a short tour of Cedar and links the four-minute introduction, in English, German, French and Spanish.
- **The desktop app no longer asks for the language twice.** On a first launch the setup window asks for the language, but the chat kept its own in the window's storage, so once setup was done it asked the same question again. The app now opens the chat with the language picked at setup (`?app-locale=` in the address, taken out again once read); a chat without a language of its own takes it, saves it on the server for scheduled runs and notifications, and doesn't ask. A language already picked in the chat is kept.

## 0.8.0

- **The desktop app can use Cedar running on another computer.** Agents run where the chat server runs, so with Cedar in the Mac or Windows app they ran only while that computer was awake and the app open. The setup page now has **Use Cedar running on another computer**: enter the address and access token of a chat server on a machine that stays on (a DGX Spark, a mini PC, another Mac sharing its chat over Tailscale), or paste the `cedar://connect` link the phone apps scan, and the app becomes a window onto that server, as the phone apps are. It starts no servers and needs no Docker or model server; agents keep running on the server while this computer sleeps, and its desktop notifications still arrive here. *Connect* checks that the server answers and accepts the token before switching; the address must be HTTPS (plain HTTP only to `localhost`). *Disconnect* goes back to the servers on this computer. Either switch restarts the app. Saved as `remote` in `config.json`.
- **The desktop app asks first how it is used.** On a first launch, after the language, the setup window asks whether to **run everything on this computer** or **connect to Cedar on another computer**, and starts nothing until it is answered: it no longer looks for Docker, starts Docker Desktop or downloads the sandbox image right away, so someone connecting to another computer isn't sent off to install Docker. The answer is kept (`run_locally` in `config.json`). Someone who set Cedar up with an earlier version is asked once too, after updating, with *keep running everything on this computer* as the first option; their servers start as before while the question is open, so scheduled agents don't stop.

## 0.7.0

- **Agents start on more than a clock.** The chat's scheduled agents become *agents*: a prompt with a trigger. - **Memory, revised.** Memory was a flat list of up to 200 facts, shown whole in every prompt and written only from the last message you sent; it was not useful. It is now typed and versioned, and used the way the research on agent memory says works (the design and the research behind it are in [docs/design/memory.md](docs/design/memory.md)). What is kept: facts, preferences and standing instructions you stated, each with the words of yours it was taken from, when it became true, and, for a fact with one current value (home city, employer), a key; temporary facts with an end date; an episode per conversation (what it was about and how it ended), written by the run itself; procedures (how a task with tools went well, abstracted); and a profile, a short summary of you that a background pass writes and that you can write yourself. What a run sees: the profile and every pinned row (instructions are pinned by default) in every request, plus what the request calls for: facts whose words overlap it, and earlier conversations and procedures only on a recall cue ("like last time", a date), within a token budget; a store of up to 25 facts is shown whole. Ids are short (`[m12]`) and what was shown goes out as a new `memory.recalled` event and in the trace as `memory`. A `recall` tool searches memory, with history, in every run. Writing: the call at the end of a run now reads the conversation (never tool results or files) and notes the facts you stated, each with your words as its quote, an episode, and a procedure when the work went well; a fact is saved only if the quote is in your own words (so nothing from a tool, a page or an email can become a fact about you), text that looks like a secret or an identifier is refused, the same thing said again is one row, a text that differs in one word is another, and a contradiction supersedes the old row and keeps it as history instead of overwriting or deleting it. `remember` takes `kind`, `supersedes`, `valid_until`, `subject` and `relation`; `forget` archives instead of deleting. Consolidation: after five finished runs (`MEMORY_CONSOLIDATE_AFTER`) or an hour of idleness, a background pass archives expired temporary facts, rolls raw episodes older than a month up into one summary per month, and makes one model call that merges duplicates, closes contradictions and writes the profile, conservatively (only rows of one kind that are plainly alike; never a pinned row; never a profile you wrote; every change an audit row; nothing deleted). Rank and budgets replace the hard cap: rows are ranked by kind, repetition, recall and disuse (down to a floor), and past `MEMORY_MAX_ITEMS` (now 500) the lowest-ranked is archived, not refused. New: `POST /v1/runs/{id}/feedback` (a thumbs up or down counts for or against the procedures the run was shown; the chat passes its thumbs on), `GET /v1/memory?kind=&archived=&q=`, `GET` and `PATCH /v1/memory/{id}` (edit, pin, archive, restore), `GET /v1/memory/{id}/history`, `GET` and `PUT /v1/memory/profile`, `GET /v1/memory/export` and `POST /v1/memory/import`; `GET /v1/defaults` reports the new limits. `MEMORY_EXPERIENCE`, `MEMORY_CONSOLIDATE`, `MEMORY_CONSOLIDATE_AFTER` and `MEMORY_RECALL_TOKENS` are new settings. Upgrading: the migration keeps every memory as a fact without a quote; clients from before this release keep working with the list (`id`, `text`, `run_id`, `created_at`, `updated_at` are unchanged).

- **OpenShell sandboxes, opt-in, with a network policy per program and host (#122).** On Linux and macOS an admin can run conversations' sandboxes, personal tool calls and tool installs in [NVIDIA OpenShell](https://github.com/NVIDIA/OpenShell) sandboxes instead of plain Docker containers: Settings → *Advanced settings* (a new page in the web chat and the Mac app) → *Run sandboxes with OpenShell*, or `PUT /v1/admin/settings` with `{"sandbox_runtime": "openshell"}`. cedar checks that OpenShell's gateway answers before it switches, and says why when it can't. Under the switch, *How to install OpenShell* gives the commands for the OS cedar runs on (macOS or Linux), with a Copy button for each. Docker stays the default, and the only runtime on Windows, where OpenShell doesn't run: the switch is greyed out there, with a note why. A switch applies from the next message: a conversation's kept container is replaced by a sandbox on the same workspace volume, so its files come along, both ways.
- In an OpenShell sandbox no process has a network of its own: each connection goes through OpenShell's supervisor, which checks the program and host against the sandbox's policy. `SANDBOX_POLICY` picks it: `offline` reaches nothing, `packages` lets Python reach PyPI and Node.js reach npm, and a path names a policy file of your own (presets in `sandbox/policies/`). Unset, it follows `SANDBOX_NETWORK` (`none` is `offline`, a network `packages`). On Docker, any policy but `offline` still gives the container all of `SANDBOX_NETWORK`, as before.
- **Blocked connections are reported and can be allowed (OpenShell).** When the policy refuses a connection, the tool result says which program tried to reach which host, and the run gets a `sandbox.denied` event. In a run with someone to ask, cedar asks (*Let curl connect to example.com:443*); *Allow* adds that program and host to the sandbox's policy for the run, *Always* also for later runs of the same key, and the model is told to try again. On OpenShell this replaces the yes-or-no question before running code with a network; on Docker that question stays.
- **Personal and registry tools only reach the hosts they declare (OpenShell).** Each call's sandbox lets the tool's Python reach those hosts on ports 80 and 443 and nothing else, and tool installs reach only PyPI. On Docker a tool that declares hosts still gets `TOOLS_NETWORK`.

- Setting OpenShell up: install it and run its gateway with `allow_driver_config = true` (and `supervisor_network_mode = "bridge"` on Docker Desktop); see *OpenShell sandboxes (opt-in)* in the README, DEPLOYMENT.md and desktop/README.md. The sandbox image's working directory is now `/sandbox` (cedar runs commands in `/workspace` either way); rebuild it with `docker build -t cedar-sandbox sandbox/`. The web browser tool always runs in its own Docker container, since a browser needs to reach any site.

## 0.1.7

- **Sandboxes are paused when a conversation goes idle.** A completed run now keeps its sandbox container for the conversation's next turn instead of removing it, so processes it started and packages it installed outside `/workspace` are still there. After `sandbox_idle_minutes` without a new turn (10 by default, 0–1440) the container is paused with `docker pause`, and the next message resumes it. Set it under Settings → Server → *Pause when idle*, or with `PUT /v1/admin/settings`. Kept containers are removed with their workspace and when cedar stops. `PUT /v1/admin/settings` now leaves out fields unchanged instead of resetting them (#85).
- **Cedar decides when to plan.** A new plan mode, `tool` (*When Cedar thinks it helps* in Settings → Plans), offers the model a `propose_plan` tool instead of planning every longer prompt: Cedar proposes steps only for requests that take several steps or tools, or that would be costly to get wrong, and waits for your go-ahead partway through the response, where you can still change them. Such a plan is marked as Cedar's in the chat, the desktop apps and the iOS and Android apps, and the phone apps get a Plans setting of their own for the messages you send from them (#84).
- **A personal assistant by default.** The default system prompt (used when `SYSTEM_PROMPT` isn't set) now frames Cedar as a personal AI assistant instead of a coding agent: it answers first, asks clarifying questions when the answer would change what it does, writes a short plan before complex tasks and carries it out (following one already agreed with `PLAN`), checks before anything it can't undo, and keeps your information private (#83).
